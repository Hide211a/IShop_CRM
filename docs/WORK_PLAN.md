# План роботи — iShop Рівне → production (Vercel + Railway)

## Що здаємо

**Тільки проєкт** — робочий застосунок онлайн + репозиторій з кодом і тестами.

**Не здаємо окремо:** пояснювальну записку, ER/USE_CASES як окремі файли для комісії, розширену документацію. Файли в `docs/` — **внутрішні нотатки для розробки**, не обов’язковий deliverable.

**Мінімум у репозиторії (для перевірки проєкту):**
- `README.md` — як запустити локально + **посилання на prod** + демо-логіни
- Код frontend + backend
- Автотести (`npm test`, опційно E2E)

---

## Мета

Довести проєкт від поточного стану (~85–90% функціоналу) до **готового, протестованого, задеплоєного** рішення, яке можна **показати на захисті по URL** без додаткових документів.

**Цільовий стек деплою:**

| Частина | Платформа | Примітка |
|---------|-----------|----------|
| Frontend (React SPA) | **Vercel** | Статичний build з Vite |
| Backend (Express API) | **Railway** | Node.js сервіс |
| База даних | **Railway PostgreSQL** | SQLite лише для локальної розробки |

> **Чому PostgreSQL на Railway?** SQLite — файл на диску; на Railway файли **не постійні** (перезапуск = втрата даних). Для production потрібна PostgreSQL. Локально залишаємо SQLite для простоти.

---

## Загальні правила на кожному етапі

Перед переходом до наступного етапу **обов’язково**:

1. Пройти чеклист тестування етапу (нижче).
2. `npm test` у `backend` — без падінь.
3. `npm run build` у `frontend` — без помилок.
4. Ручна перевірка 1–2 ключових сценаріїв у браузері.

*(Оновлення `docs/` — лише якщо потрібно для себе; на здачу не впливає.)*
